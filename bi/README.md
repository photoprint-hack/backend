# Защищённый Metabase для Photoprint

Код Backend выдаёт пятиминутные подписанные ссылки на разрешённые dashboard. Изоляция manager зависит от того, что **каждая карточка** использует закреплённое подразделение. Этот каталог содержит SQL и процедуру настройки; действующий Metabase в рамках локальной реализации не создавался и не проверялся.

## Два подключения к PostgreSQL

Metabase нужны независимые подключения:

1. **Application database** — постоянная отдельная PostgreSQL для настроек, пользователей и dashboard самого Metabase. Не используйте локальную H2 в эфемерном контейнере Render.
2. **Аналитический источник** — база Photoprint через роль `photoprint_bi`, которой разрешены только BI views. Не передавайте пароль владельца приложения в это подключение.

После миграций выполните [setup_readonly.sql](setup_readonly.sql) через `psql` под владельцем базы с правом CREATE ROLE. Подключение задавайте средствами вашего клиента; не коммитьте строку с паролем. Скрипт рассчитан на схему `public`, создаёт отдельную роль, выдаёт SELECT на восемь views и интерактивно запрашивает пароль. Если роль уже имеет повышенные права, членство или доступ к базовым таблицам через существующие/PUBLIC grants, операция откатывается. Сначала ограничьте такие права отдельно с администратором БД; скрипт не меняет права PUBLIC.

Список views:

- `v_dashboard_kpi` — сохранённые KPI с явными периодами и контекстом;
- `v_revenue_by_day` — завершённые заказы по календарю Минска;
- `v_orders_by_status` — статусы заказов;
- `v_sales_plan_fact` — дневная выручка и план;
- `v_production_quality` — выпуск и дефектные единицы;
- `v_support_sla` — закрытые обращения и SLA;
- `v_staffing_coverage` — кадровые агрегаты без персональных данных;
- `v_capacity_forecast` — сохранённый прогноз мощности.

Под BI-ролью `SELECT * FROM public.v_revenue_by_day LIMIT 1` должен работать. Чтение `users`, `refresh_tokens`, `audit_logs` и `orders` должно завершаться отказом в доступе. Роль имеет общую видимость разрешённых агрегатов, поэтому её реквизиты получает только закрытый Metabase, а manager — только embed с закреплённым подразделением.

## Отдельный сервис Render

Создайте отдельный Web Service из официального образа `metabase/metabase`, закрепив конкретную версию или digest выбранного релиза. В этом репозитории версия Metabase не зафиксирована и совместимость конкретного Docker-образа не проверялась. Подберите тариф с достаточной памятью для JVM; бесплатный Backend Blueprint не задаёт тариф Metabase.

Задайте секретные настройки Metabase:

| Переменная | Назначение |
| --- | --- |
| `MB_DB_TYPE=postgres` | Постоянная application database |
| `MB_DB_CONNECTION_URI` | `jdbc:postgresql://<host>:<port>/<metabase_database>?sslmode=require` |
| `MB_DB_USER`, `MB_DB_PASS` | Пользователь и пароль application database |

Application database должна существовать заранее, её схема — `public`. Эти реквизиты не относятся к роли `photoprint_bi`. Сетевой порт Metabase по умолчанию 3000; направьте Render на этот порт либо задайте Jetty port в настройках выбранной версии. HTTP health endpoint Metabase — `/api/health`. Проверьте доступность HTTPS-адреса, завершите первичную настройку администратора, ограничьте доступ к административным аккаунтам. Manager не выдаётся аккаунт общего Metabase.

Добавьте базу Photoprint как аналитический PostgreSQL источник с отдельным BI-логином, включите TLS по требованиям провайдера. Отключите public sharing; используйте signed static embedding. Сгенерируйте отдельный embedding secret, храните его в настройках Metabase и `METABASE_EMBEDDING_SECRET` Backend. Это не JWT-секрет приложения.

## Карточки и locked-параметры

[questions.sql](questions.sql) содержит пять самостоятельных запросов: дневная выручка, план/факт, брак, SLA и HR. Создайте native SQL questions с этими запросами. `date_from`, `date_to`, `department_id`, `product_id` — **обязательные текстовые переменные**; даты приводятся к SQL date в запросе. Не используйте optional `[[...]]` для фильтра подразделения.

Создайте пять dashboard с ключами `company`, `production`, `finance`, `support`, `hr`. Company содержит карточки выручки и плана/факта, finance — плана/факта, остальные — соответствующие карточки. Добавьте четыре параметра с этими точными slug и свяжите каждый с переменной **каждой** карточки. В настройках signed embed установите все четыре параметра в Locked и сохраните изменения.

Backend отправляет:

```json
{
  "department_id": "<UUID из профиля manager>",
  "product_id": "all",
  "date_from": "2026-11-01",
  "date_to": "2026-11-12"
}
```

Значение `company` вместо UUID означает общую область и выдаётся только разрешённым общим ролям. `all` означает отсутствие продуктового фильтра. Не подменяйте их пустыми массивами: пустой locked-параметр может отключить фильтр. HR игнорирует продукт по согласованному контракту, но параметр всё равно присутствует в карточке и токене; UI показывает соответствующее уведомление.

Установите Backend:

```dotenv
METABASE_URL=https://<metabase-service>.onrender.com
METABASE_DASHBOARD_IDS={"company":1,"production":2,"finance":3,"support":4,"hr":5}
METABASE_VERIFIED_DASHBOARDS=[]
```

ID выше — пример, замените реальными. До проверки оставьте VERIFIED пустым: API возвращает 503, не создаёт небезопасную ссылку.

## Проверка перед включением

1. Под director откройте dashboard за месяц; сравните выручку и план/факт с API при тех же датах и фильтрах.
2. Под manager сравните **каждую** карточку с API своего подразделения. В демоданных общая выручка отличается от выручки подразделения, что позволяет заметить потерянный фильтр.
3. Запрос manager с чужим `department_id` должен дать 403. Изменение iframe query string не должно расширять область. Подмена JWT должна отклоняться Metabase; просроченная ссылка — перестать работать.
4. Убедитесь, что manager не получает общий BI-аккаунт/публичную ссылку и не может открыть чужие карточки через несвязанные drill-through или общие ссылки. Отключите такие переходы, если они расширяют область.
5. Отметьте проверенные ключи в `METABASE_VERIFIED_DASHBOARDS`, например `["company","production","finance","support","hr"]`, и перезапустите Backend. Повторите проверку в настоящем Frontend iframe, включая обновление истёкшего токена.

Локальные тесты проверяют подпись и область JWT, SQL-шаблоны и ограничения роли PostgreSQL. Они не заменяют эту проверку реально настроенного Metabase.

Настройки сверены с официальными документами [application database](https://www.metabase.com/docs/latest/installation-and-operation/configuring-application-database), [signed embedding](https://www.metabase.com/docs/latest/embedding/securing-embeds) и [Render Blueprint](https://render.com/docs/blueprint-spec).
