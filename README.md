# Photoprint backend — управленческая платформа

Backend трека 1 хакатона: 12 KPI, заказы и CRM-воронка, производство, финансы и HR,
цепочка «отклонение → решение → задача → проверка результата», прогноз на четыре
недели, импорт пяти источников, качество данных и аудит. Все демосуммы синтетические,
валюта BYN.

- Опубликованный API: [backend-v8pa.onrender.com](https://backend-v8pa.onrender.com).
- Swagger: [backend-v8pa.onrender.com/docs](https://backend-v8pa.onrender.com/docs).
- OpenAPI: [backend-v8pa.onrender.com/openapi.json](https://backend-v8pa.onrender.com/openapi.json).
- Frontend: [photoprint-frontend.vercel.app](https://photoprint-frontend.vercel.app).

Стек: Python 3.13, FastAPI, PostgreSQL 15+, SQLAlchemy async, Alembic.
Версии и лицензии пакетов — в [THIRD_PARTY_LICENSES.md](THIRD_PARTY_LICENSES.md).

## Быстрый запуск

Нужны `uv`, Docker или уже установленный PostgreSQL 15+, и Node.js для frontend.
Команды ниже выполняются из корня Backend.

### 1. Подготовить PostgreSQL

Если PostgreSQL ещё нет, для локальной демонстрации можно запустить контейнер:

```sh
docker run --name photoprint-postgres --rm \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=photoprint \
  -p 5432:5432 \
  -d postgres:17
```

Пароль `postgres` показан только для локального контейнера. Если порт `5432`
занят, используйте установленный PostgreSQL и измените `DATABASE_URL`.

### 2. Установить зависимости и настроить `.env`

```sh
uv sync --frozen
cp -n .env.example .env
```

В `.env` обязательно задайте:

- `DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/photoprint`;
- `JWT_SECRET_KEY` длиной не менее 32 байт;
- пять разных `DEMO_*_PASSWORD` длиной 12–128 символов.

Секрет можно сгенерировать командой:

```sh
uv run python -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Не заменяйте существующий `.env` шаблоном. Обычный PostgreSQL URL и
`postgresql+asyncpg://` поддерживаются; `sslmode=require` преобразуется для
asyncpg. Для облачного transaction pooler задайте прямое/session-соединение в
`MIGRATION_DATABASE_URL`.

### 3. Создать схему и демоданные

Следующие команды **меняют базу из `.env`**. Перед запуском проверьте её назначение:

```sh
uv run alembic upgrade head
uv run python scripts/seed.py
```

Seed создаёт 500 заказов, 200 клиентов, 300 обращений, сделки, производство,
финансы, HR, дневные планы, критическое отклонение и дефицит мощности. Обычный
повторный seed добавляет отсутствующие записи и сохраняет пароли и действия
пользователей.

### 4. Запустить API

```sh
./start.sh --reload
```

Сервер: [http://localhost:8000](http://localhost:8000).
Health: [http://localhost:8000/health](http://localhost:8000/health). `GET /health`
возвращает 200 при доступной БД и 503 при недоступной. Переменная `PORT` меняет
порт. `start.sh` не запускает миграции или seed автоматически.

### 5. Запустить frontend

Frontend находится в отдельном репозитории `photoprint-frontend`, каталог с
`package.json` — `photoprint-frontend/frontend`.

```sh
cd ../photoprint-frontend/frontend
npm ci
cp -n .env.example .env.local
```

Для локального API установите в `.env.local`:

```env
VITE_API_URL=http://localhost:8000/api/v1
VITE_USE_MOCKS=false
```

Затем:

```sh
npm run dev
```

Интерфейс откроется на [http://localhost:5173](http://localhost:5173). Если нужен
только UI без PostgreSQL и Backend, задайте `VITE_API_URL=` и
`VITE_USE_MOCKS=true`.

`DEMO_REFERENCE_DATE=YYYY-MM-DD` фиксирует опорную дату при первоначальном
заполнении; без него используется текущая дата Минска. Для новой демонстрационной
даты создайте отдельную базу: обычный seed не переносит уже созданные факты.

## Демо-учётные записи

| Логин | Пароль из окружения | Доступ |
| --- | --- | --- |
| `admin@fotoprint.demo` | `DEMO_ADMIN_PASSWORD` | Администрирование, импорт, все данные |
| `director@fotoprint.demo` | `DEMO_DIRECTOR_PASSWORD` | Все бизнес-данные и операции, чтение аудита |
| `manager@fotoprint.demo` | `DEMO_MANAGER_PASSWORD` | Свое подразделение, финансовые и HR-агрегаты |
| `analyst@fotoprint.demo` | `DEMO_ANALYST_PASSWORD` | Чтение бизнес-данных, проверки качества |
| `production.manager@fotoprint.demo` | `DEMO_MANAGER_PASSWORD` при первом seed | Руководитель производства, отдельная область и получатель эскалаций |
| `employee@fotoprint.demo` | `DEMO_EMPLOYEE_PASSWORD` | Свои задачи и прямо связанные заказы/решения |

Seed требует все пять паролей. В Backend-репозитории пароли не хранятся; текущие
публичные значения синтетических демоаккаунтов дублируются frontend-репозиторием
для автоподстановки, поэтому при ротации их нужно синхронизировать. `POST /api/v1/demo/reset`
доступен только admin при `DEMO_MODE=true` вне production и требует
`{"confirm":"RESET_DEMO_DATA"}`. Он восстанавливает известные демозаписи, архивирует
задачи и сохраняет историю/аудит/пароли. При обнаружении сторонних фактов возвращает
409. Для production маршрут не регистрируется.

## Shell-обёртки

В корневой папке `sh/` есть исполняемые обёртки для Python-скриптов из `scripts/`. Они сами переходят в корень проекта, передают аргументы и возвращают код завершения Python-процесса. Нужны `uv` и установленное окружение проекта (`uv sync --frozen`).

| Обёртка | Назначение и побочные действия |
| --- | --- |
| `./sh/seed.sh` | Загружает демоданные в БД из `.env`; требует миграции и пять DEMO-паролей. |
| `./sh/import_data.sh crm data/mock/crm.json` | Импортирует файл в БД; принимает те же аргументы, что Python CLI. Относительный путь считается от корня проекта. |
| `./sh/export_openapi.sh` | Перезаписывает корневой `openapi.json`; другой путь задаётся через `--output`. |
| `./sh/start_server.sh` | Запускает сервер через deployment entrypoint: по умолчанию сначала применяет миграции. Для запуска без миграций задайте `MIGRATE_ON_START=false`. |
| `./sh/worker.sh` | Непрерывный процесс уведомлений/SLA; использует БД из `.env`, без миграций и seed. `--once` выполняет один проход. |
| `./sh/check_ai.sh --live` | Один реальный запрос OpenRouter на фиксированном синтетическом примере, без БД. Без `--live` проверяет только наличие настройки; ключ не печатает. |
| `./sh/test_postgres.sh -q` | Запускает полный набор тестов на отдельной временной PostgreSQL; удалённая БД не используется. |

`./start.sh --reload` остаётся обычным запуском для разработки без автоматических миграций. Проверяйте назначение `DATABASE_URL` перед seed, импортом и запуском с миграциями.

## Подключение Frontend

- Базовый URL: `/api/v1`. Объекты — `{data: ...}`, списки — `{items,total,page,page_size,pages}`. Ошибки — `{detail:{code,message,fields,request_id}}`.
- `POST /auth/login`: JSON `email`, `password`. Access JWT возвращается в `data.access_token`; передавайте `Authorization: Bearer ...`. Срок — 15 минут.
- Refresh хранится в HttpOnly Cookie на `/api/v1/auth`; `POST /auth/refresh` и `/auth/logout` отправляются с `credentials: "include"`. Срок refresh — 7 дней, ротация обязательна. Повторное использование старого refresh отзывает семейство.
- `FRONTEND_URL` — один точный origin, без пути. В локальной разработке `http://localhost:5173`, Cookie Secure=false/SameSite=lax. Для отдельных HTTPS-сайтов задайте `APP_ENV=production`, `COOKIE_SECURE=true`, `COOKIE_SAMESITE=none`, HTTPS `FRONTEND_URL`/`BACKEND_URL`. Cookie-операции проверяют Origin.
- Создание заказа, решения и задачи требует UUIDv4 в `Idempotency-Key`. Повтор с тем же телом возвращает исходные статус/ответ, другой запрос с тем же ключом — 409. Срок ключа 24 часа. PATCH требует актуальный `version`; конфликт — 409.
- Manager видит кампании, связанные с заказами/сделками своего подразделения, включая общие. `CampaignOut.budget` — `number|null`: для manager всегда `null`, для остальных разрешённых ролей — общий бюджет.
- UI может использовать `allowed_actions`; сервер независимо проверяет права. Чужое подразделение в фильтре manager даёт 403, недоступный объект по UUID — 404.
- Периоды `date_from`/`date_to` включительны, календарь `Europe/Minsk`, время хранится в UTC. Неизвестные query-параметры отклоняются; диапазон ограничен 366 днями. Для `GET /metrics/{code}/history` с `interval=day` (по умолчанию) максимум — 31 календарный день включительно; больший диапазон возвращает 422. Для длинных периодов используйте `interval=week` или `interval=month` (до 366 дней).
- `null`/`no_data` означает отсутствие источника или неопределённую долю. Пустая загруженная сумма/счётчик — 0. HR и общие расходы не распределяются по продуктам; ответ содержит `ignored_filters`.

Группы API: `/users`, `/departments`, `/products`, `/customers`, `/campaigns`, `/orders`, `/sales/*`, `/production/*`, `/finance/*`, `/hr/summary`, `/support/interactions`, `/dashboard`, `/metrics`, `/alerts`, `/decisions`, `/tasks`, `/forecast`, `/integrations`, `/data-quality/*`, `/audit-logs`. Точные тела и ответы — в OpenAPI. Для передачи схему можно выгрузить без соединения с БД:

```sh
uv run python scripts/export_openapi.py
```

Пишется `openapi.json` в корне; production-схема по умолчанию исключает демонстрационный reset.

## Импорт источников

Admin отправляет `POST /api/v1/integrations/{source}/import`, где source: `crm`, `erp`, `finance`, `support`, `hr`. Максимум 1000 записей и 5 MiB. Сущности:

| Источник | entity_type |
| --- | --- |
| crm | customer, campaign, deal, deal_event |
| erp | department, product, order, order_event, production_record, capacity_plan |
| finance | finance_record |
| support | support_interaction |
| hr | hr_snapshot |

```json
{"records":[{"entity_type":"customer","external_id":"CRM-C-201","event_at":"2026-11-12T09:00:00Z","data":{"name":"Демо-клиент","customer_type":"b2b","segment":"corporate","acquisition_channel":"website"}}]}
```

Повторный `(source, entity_type, external_id)` обновляет запись, старое событие пропускается; ошибки возвращаются поштучно. Корректные записи сохраняются даже при частичном успехе и отдельной ошибке перерасчёта. Ссылки принимают платформенный UUID либо объект `{source,entity_type,external_id}` связанной сущности. Связанные [JSON/CSV-примеры](data/mock/README.md) поставляются для всех пяти источников. Рекомендуемый порядок: подразделения/продукты/клиенты → кампании/заказы/сделки → события/производство/финансы/поддержка/HR. Подробные ограничения проверяются перед сохранением.

CLI использует тот же обработчик и активного admin:

```sh
uv run python scripts/import_data.py crm /absolute/path/customers.json
uv run python scripts/import_data.py crm /absolute/path/customers.csv --actor-email admin@fotoprint.demo
```

CSV имеет четыре колонки: `entity_type,external_id,event_at,data`; `data` — JSON в корректно экранированной CSV-ячейке. Проверки качества запускают admin/analyst; история загрузок и результаты доступны через API.

## KPI и управленческий цикл

Расчёты выполняет Backend. Проценты агрегируются из числителей и знаменателей. Новые клиенты определяются по первой завершённой покупке за всю историю в выбранной области; брак — по единицам продукции; SLA — по закрытым обращениям с заданным сроком; HR — по последнему снимку каждого подразделения не позже конца периода.

Отклонение от плана до 5% включительно — normal, свыше 5% до 10% — warning, свыше 10% — critical; для брака хуже рост, для целевых KPI — снижение. Загрузка мощности: <70% warning, 70–100% normal, >100–110% warning, >110% critical. Это настройки демонстрационной модели.

`POST /metrics/recalculate` выполняет admin. Он сохраняет значения и создаёт критические Alert для месячных контекстов. GET Dashboard не создаёт Alert. Один KPI/месяц/подразделение/продукт имеет один Alert; resolved не переоткрывается автоматически. Задачи создаёт пользователь. Завершение задачи не завершает решение: нужны `actual_result`, статус needs_review, затем подтверждение с `verification_note`.

Прогноз сравнивает нормо-часы спроса и мощности. Используется средний спрос четырёх завершённых недель по созданным неотменённым заказам и планы следующих четырёх полных недель. Отсутствие истории или плана отражается как no_data. Дефицит и резерв возвращаются раздельно, без отрицательных величин.

## Карта, обращения и фоновые процессы

Перед запуском расширения примените новые миграции и выполните обычный seed на выбранной БД. Это изменяющие БД команды из раздела локального запуска. Миграции `20261112_03`–`20261112_05` добавляют семь таблиц; существующие таблицы и UUID сохраняются. Обычный seed добавляет ответственность и демонстрационные обращения, сохраняя существующие пароли и действия. Reset отменяет активные обращения до архивации задач и создаёт новые синтетические примеры.

Карта доступна через `GET /api/v1/impact-map`; карточка узла — `/impact-map/nodes/{node_id}`, соседи — `/impact-map/nodes/{node_id}/neighbors`, направленный путь — `/impact-map/paths?from_node_id=...&to_node_id=...`. UUID узла относится к визуальной проекции; настоящий идентификатор хранится в `entity_ref`. Фильтры совпадают с Dashboard. Ответ ограничен 200 узлами/400 рёбрами, `truncated` обозначает ограниченную проекцию. BFS работает только по разрешённым вершинам. Значения KPI вычисляет исходный сервис.

`/management-actions` создаёт черновик. Все POST-команды обращения требуют `Idempotency-Key` UUIDv4 и текущую `version`; replay сохраняет исходные тело и HTTP-статус. `send` создаёт ровно одну обычную Task либо связывает подходящую активную Task того же подразделения и получателя. `reminder`/`explanation_request` обходятся без Task. `acknowledge` отличается от начала работы, доставки и прочтения. Результат проверяет другой уполномоченный пользователь. Task и Decision автоматически не отменяются и Decision не завершается. Прямой прежний PATCH Task отражается в обращении; архивирование Task отменяет активную коммуникацию.

Обращение сохраняет исходный снимок выбранных KPI/фильтров для admin/director/analyst и отдельный снимок того же периода по целевому подразделению. Manager получает только снимок своего отдела; employee получает разрешённый контекст обращения без общих KPI. Повтор запроса после утраты прав не возвращает прежний общий снимок. Текущие фильтры Dashboard не переписывают сохранённые снимки.

Назначения задаются через `PUT /responsibilities/departments/{id}` и `/responsibilities/metrics/{code}`; `version=0` создаёт отсутствующее назначение. Только admin/director изменяют назначения. Руководитель подразделения и director эскалации задаются явно. Employee видит свои обращения, а ссылки на бизнес-объекты повторно проходят прежние проверки доступа.

Для уведомлений и автоматических эскалаций нужен отдельный непрерывный процесс:

```sh
./sh/worker.sh
```

Для одного прохода: `./sh/worker.sh --once`. Worker использует ту же БД, что web; не запускает миграции или seed. В контейнере команда процесса — `python scripts/worker.py`. На Render необходимо отдельно настроить непрерывный worker с тем же окружением. Текущий `render.yaml` создаёт только web-сервис; сам web не запускает worker. Конфигурация непрерывного процесса и фактический деплой ещё не проверены.

Изменение обращения, аудит и outbox атомарны. Worker резервирует записи с lease 60 секунд, материализует уникальное внутреннее уведомление и восстанавливает истёкшие lease. Повторы: 10/30/120/300/900 секунд, затем failed. `/management-actions/{id}/delivery` показывает состояние доставки; уполномоченный руководитель может повторить failed через `/delivery/{outbox_id}/retry`. `/notifications` возвращает только свои доступные уведомления. Клиент отдельно вызывает `/notifications/{id}/delivered` и `/read`; чтение списка не изменяет их статус и не подтверждает обращение.

Календарь: Europe/Minsk, Пн–Пт 09–13 и 14–18. `BUSINESS_HOLIDAYS` — JSON-массив дат. Все приоритеты используют рабочие минуты: critical=30, high=240, medium=480, low=960. Срок выполнения Task задаётся отдельно и остаётся обычным UTC timestamp. Новое назначение запускает новый цикл реакции; изменение срока не сбрасывает уже отправленные эскалации. Сохранённая версия календаря не меняет сроки задним числом.

## OpenRouter и simulated Mary

Задайте `OPENROUTER_API_KEY` только в приватном окружении web. `OPENROUTER_MODEL=openrouter/free`; допускаются также модели с суффиксом `:free`. Платные маршруты запрещены настройкой и нулевым `provider.max_price`. Backend требует поддержку JSON Schema и повторно валидирует ответ. Ключ, личные данные, переписки и бизнес-тексты в контекст не передаются. Демонстрационный контекст должен содержать только синтетические данные.

`POST /impact-map/analyze` принимает `request_key` UUIDv4, `metric_code`, `context` и актуальную `graph_revision`. Backend формирует контекст; AI возвращает анализ и `draft_text`, не отправляет обращения и не выполняет команды. Факты и рассчитанные зависимости устанавливает сервер; неизвестные ссылки отклоняются, корреляции без расчёта остаются пустыми. При смене данных/прав старый контекст отклоняется. Кэш изолирован по пользователю, роли, области, ревизии, prompt и модели; TTL до 900 секунд, общий лимит максимум 40 попыток за сутки UTC. Одновременные одинаковые запросы используют одну попытку. Ошибки 429 автоматически не повторяются; результат LLM не заменяется шаблоном.

Проверка конфигурации: `./sh/check_ai.sh`. Один реальный запрос с фиксированными синтетическими цифрами: `./sh/check_ai.sh --live`. Этот диагностический CLI не обращается к БД и не расходует серверный счётчик 40 попыток; каждый запуск `--live` использует квоту аккаунта OpenRouter. Сетевую доступность подтверждает только результат живого вызова, не тест с mock provider.

`POST /integrations/mary/events` доступен admin и принимает `records`: `external_id`, `event_type`, `occurred_at`, `department_id`, необязательный `order_id`, `channel=web|phone|demo`. Времена с часовым поясом; будущее отклоняется. Идентификатор и время события обеспечивают upsert/replay; корректные записи сохраняются при ошибках ссылок в других записях. Mary явно simulated; переписка и произвольные персональные metadata не принимаются. Прежние пять импортов не менялись.

## Изменение аналитической интеграции

Интеграция Metabase удалена: `/api/v1/analytics/metabase-embed` больше не существует (404), переменные `METABASE_*` не используются. Dashboard, KPI, сводки и прогноз доступны через API приложения. Frontend должен убрать iframe и запросы к удалённому endpoint.

Миграция `20261112_06` удаляет восемь SQL views бывшей интеграции, сохраняя таблицы и данные приложения. Предыдущие ревизии сохранены для существующих баз; downgrade восстанавливает определения views без прежних грантов. Миграция применяется обычным запуском Alembic или при старте контейнера. Отдельная роль PostgreSQL, если её создавали вручную, автоматически не удаляется.

## Render и Docker

[render.yaml](render.yaml) описывает Backend с автоматическим деплоем из Git; секреты вводятся в Render, в YAML их нет.

GitHub CI запускает Ruff и тесты на PostgreSQL 17, проверяет актуальность OpenAPI, собирает Docker-образ и сканирует его. Результат текущего релиза проверяйте в GitHub Actions; локальные тесты не подтверждают выполнение CI. Автодеплой Render пока настроен на каждый commit, независимо от результата CI; для обязательного ожидания проверок выберите соответствующий режим в Render.

Dockerfile запускает приложение непривилегированным пользователем. Команда контейнера `python scripts/start_server.py` сначала выполняет Alembic под PostgreSQL advisory lock, затем запускает Uvicorn. Ошибка миграции останавливает старт; seed при деплое не запускается. Для session advisory lock нужен прямой/session URL в `MIGRATION_DATABASE_URL`. Если миграции выполняются отдельным процессом перед стартом приложения, задайте `MIGRATE_ON_START=false`.

Для нового Render Docker-сервиса укажите этот репозиторий, ветку `main`, корневой Dockerfile, Free compute и health check `/health`. Задайте `APP_ENV=production`. Обязательны `DATABASE_URL`, `JWT_SECRET_KEY`, HTTPS `FRONTEND_URL`/`BACKEND_URL`, production Cookie-параметры. Для первоначального заполнения выделенной демобазы запустите локально `./sh/seed.sh` с подключением к выбранной БД и пятью DEMO-паролями; seed меняет данные. Render Secret Files/env используются вместо коммита `.env`.

```sh
docker build -t photoprint-backend .
docker run --rm --env-file .env -p 8000:8000 photoprint-backend
```

Внутри Docker `localhost` указывает на контейнер: строка БД должна вести к доступному хосту. Устаревшее копирование `bi/` удалено из Dockerfile. Сборка Docker-образа после этой правки ещё не проверена. Деплой на Render и работа с удалённой PostgreSQL требуют отдельной проверки в целевом окружении.

При неудачном релизе верните предыдущий успешный deploy в Render и проверьте `/health`, login и Dashboard. Миграции автоматически назад не откатываются. Перед миграциями сохраняйте резервную копию; downgrade удаляет данные и применяется только к заведомо одноразовой базе.

## Проверки

Тесты разделены по проверяемой границе. Общие фикстуры находятся в `tests/conftest.py`.

| Группа | Назначение | Отдельный запуск |
| --- | --- | --- |
| `tests/unit/` | Изолированные функции, валидация, календарь, BFS, security и mock адаптеров; без БД | `uv run pytest -q tests/unit` |
| `tests/api/` | HTTP-контракты, роли, workflow и ответы endpoint; большинство используют PostgreSQL | `./sh/test_postgres.sh -q tests/api` |
| `tests/integration/` | Прямые проверки seed, миграций, worker/outbox, импорта файлов и shell-процессов | `./sh/test_postgres.sh -q tests/integration` |

API-тест может использовать БД для подготовки и проверки сохранения данных. В `integration` проверяемая граница — взаимодействие сервисов, SQL или процесса, а не HTTP-ответ. Реальные сетевые AI-запросы в автоматические группы не входят; provider подменяется mock.

Быстрые проверки без БД:

```sh
uv run ruff check app scripts tests
uv run pytest -q tests/unit tests/api/test_http_contract.py
```

Полный набор с собственной временной PostgreSQL, без Docker и удалённой БД:

```sh
uv run --python 3.12 --no-project --with pgserver python scripts/test_postgres.py -q
```

Python 3.12 нужен только оболочке `pgserver` с готовыми бинарниками. Она запускает тесты интерпретатором проекта Python 3.13, создаёт временный сервер и удаляет его после выполнения. Требуются доступ к пакетам при первом запуске и право запускать локальные процессы/сокеты.

Либо задайте `TEST_DATABASE_URL` на отдельную тестовую PostgreSQL 15+ и выполните `uv run pytest -q`. Тесты создают и удаляют случайные схемы. Не указывайте production: тестовая роль должна иметь права CREATE SCHEMA. Без `TEST_DATABASE_URL` проверки, которым нужна БД, явно пропускаются в обеих группах `api` и `integration`. Unit-группа и `tests/api/test_http_contract.py` БД не требуют. GitHub Actions запускает три группы отдельными шагами.

Проверяются ротация refresh/reuse, роли и изоляция подразделений, полный жизненный цикл решений/задач, история, конкурентные PATCH и Idempotency-Key, KPI/пороговые значения, seed, частичный импорт, качество, прогноз, финансовая сверка. Визуальный Frontend этими тестами не проверяется.

Результат на 2026-11-12: полный набор на временной PostgreSQL — **131 passed**;
`tests/unit` + HTTP-контракт — **48 passed**; Ruff и format-check — без ошибок.
Опубликованный `/health` вернул HTTP 200 с подключённой базой.

## Структура

- `app/api/v1/` — маршруты и права на действия.
- `app/schemas/` — предметные пакеты `catalog/`, `workflow/`, `analytics/`, `reporting/`, `integrations/`, общие query/ссылки/история в `shared/`. Пакет `impact/` содержит контракт карты, обращений и AI; `identity.py` — пользователей и авторизацию, `common.py` — общие типы и обёртки ответов. Импорты идут из конкретных предметных модулей; прежние `domain.py` и `responses.py` удалены.
- `app/services/` — бизнес-правила, расчёты, импорт, аудит; `scoping.py` — общие фильтры и экранирование поиска, `impact/` — карта, AI, обращения, уведомления и SLA.
- `app/core/` — настройки, безопасность, права, обработка ошибок и именованные advisory locks в `locks.py`.
- `app/models/` — 36 таблиц PostgreSQL в пакетах `orders/`, `analytics/`, `reporting/`, `operations/`, `impact/`; `identity.py` и `workflow.py` объединяют небольшие связанные модели. `alembic/versions/` — фиксированные миграции.
- `app/seed/` — `service.py` координирует этапы из `stages/`: справочники, заказы, поддержка, планы, источники, workflow и сценарии impact. `context.py` хранит состояние загрузки и стабильные идентификаторы; порядок этапов и транзакция сохраняются.
- `scripts/` — seed, импорт, экспорт OpenAPI, старт с миграциями, изолированные тесты.
- `sh/` — Bash-обёртки этих Python-скриптов; запускаются из любой директории.
- `tests/api/`, `tests/unit/`, `tests/integration/` — HTTP-контракты, изолированные функции и взаимодействие с БД/процессами; общие фикстуры в `tests/conftest.py`.

Локальные `agents.md` и `ASSUMPTIONS.local.md` намеренно исключены из Git и содержат координацию и допущения этой рабочей копии. Каталог `docs/` также исключён существующими пользовательскими правилами: для другого клона передайте согласованные ТЗ отдельно. Текущий исполняемый контракт экспортируется из кода.

## Подключённый frontend и серверные mock-источники

Frontend: `https://photoprint-frontend.vercel.app`, API: `https://backend-v8pa.onrender.com/api/v1`.
Для этого раздельного HTTPS-размещения в Render нужны `APP_ENV=production`,
`FRONTEND_URL=https://photoprint-frontend.vercel.app`, `BACKEND_URL=https://backend-v8pa.onrender.com`,
`COOKIE_SECURE=true`, `COOKIE_SAMESITE=none`. Эти значения внесены в Blueprint;
для уже созданного вручную сервиса настройте их в Environment. Локальный YAML
не меняет окружение такого сервиса. Браузер должен разрешать cookie между этими сайтами.

Ввод дедлайна только датой на frontend означает конец дня Минска:
`YYYY-MM-DDT23:59:59.999+03:00`. Сотрудник отправляет только `version/status`
своей Task. `mine=true` фильтрует Task по текущему пользователю; `product_id`
у Decision проверяет явную связь через Alert или незархивированную Task с Order.
`alert_title` недоступен employee. Карточка Alert включает только явно связанные
задачами заказы; причины из связанных Decision отмечаются как требующие проверки.
`ProductionOut.planned_capacity` — дневной план для точной пары подразделение/продукт,
не доля мощности отдельного заказа; отсутствующий план — `null`.

Раздел аналитики frontend использует обычные KPI history/sales/production API
для графиков. Metabase и кнопки импорта в frontend удалены. Серверный импорт и
JSON/CSV CLI сохранены.

`GET /api/v1/mock-sources/{source}/records?page=1&page_size=20` — отдельная имитация
внешних источников на данных этой БД. `source`: `crm`, `erp`, `finance`, `support`, `hr`.
Доступен только admin с Bearer JWT. Ответ: `{items,total,page,page_size,pages}`;
запись: `{entity_type,external_id,event_at,data}`. Типы сущностей совпадают с таблицей
источников в разделе импорта. `event_at` — `updated_at`, либо `created_at`, если
обновление отдельно не хранится. Внешний ID берётся из provenance, затем из
записи, иначе используется её UUID. Порядок: группы сущностей в порядке реестра,
внутри группы — UUID; размер страницы 1–100. Пустая БД возвращает пустой список.

Mock-эндпоинт читает существующие бизнес-записи, не генерирует факты, не обновляет
метки синхронизации и не запускает импорт, seed или перерасчёт. Это имитация выдачи
CRM/ERP и остальных источников, а не коннектор к настоящей CRM. UUID-ссылки в
`data` относятся к текущей БД; перенос в другую БД требует сопоставления ссылок.
Обычные экраны frontend эти маршруты не используют.
